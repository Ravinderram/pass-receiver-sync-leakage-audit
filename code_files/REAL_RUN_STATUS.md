# Real-data run: status

## Local dataset mode (added after the figshare block)

The project now reads a locally downloaded dataset and will not touch the
network. Set ONE variable in `config.py`:

```python
IDSSE_LOCAL_DATA_DIR = r"C:\Users\ranjit\Downloads\IDSSE"
```

then

```bash
python step0_inspect_local_data.py
python step1_load.py --all
python verify/reproduce_all.py --with-data --with-pretrain
```

This was implemented and tested here against DFL-format XML generated by
`_selftest_local_xml.py` and parsed with floodlight's own
`read_position_data_xml` / `read_event_data_xml`. The local path was exercised
end to end: index, parse, cache, cache invalidation on a changed source file,
steps 2 to 5, the canonical run, every experiment, and the verification stages.
The numbers from that exercise are meaningless and are labelled `quick-`; what
it establishes is that the local loader works.


**The real-data production run was NOT executed in the environment where this
package was prepared. No real-data numbers exist in this archive, and none are
claimed.**

`work/` and `figures/` ship empty on purpose. Every synthetic and quick-mode
artefact from earlier development was removed rather than shipped, so there is
nothing here that could be mistaken for a result.

## What was attempted, and the exact failure

The project downloads the dataset through
`floodlight.io.datasets.IDSSEDataset`, which fetches from figshare. Every
attempt was refused by this environment's egress proxy:

```
$ curl -D- https://ndownloader.figshare.com/files/51643475
HTTP/2 403
x-deny-reason: host_not_allowed
Host not in allowlist: ndownloader.figshare.com.
Add this host to your network egress settings to allow access.
```

```
$ python -c "from floodlight.io.datasets import IDSSEDataset; IDSSEDataset(match_id='J03WMX').get('J03WMX')"
urllib.error.HTTPError: HTTP Error 403: Forbidden
```

The same refusal applies to every route to the data:

| Host | Purpose | Result |
|---|---|---|
| `ndownloader.figshare.com` | the 21 dataset files floodlight fetches | 403 `host_not_allowed` |
| `figshare.com` | dataset landing page | 403 `host_not_allowed` |
| `doi.org/10.6084/m9.figshare.28196177` | the DOI in the paper | 403 `host_not_allowed` |
| `nature.com/articles/s41597-025-04505-y` | the paper | 403 `host_not_allowed` |
| `zenodo.org` | possible mirror | 403 `host_not_allowed` |

The allowlist for this environment is limited to package registries
(`pypi.org`, `files.pythonhosted.org`, `npmjs.org`, `crates.io`) and
`github.com` / `raw.githubusercontent.com`.

GitHub is reachable, so the official companion repository was checked as a
possible mirror:

```
$ curl https://api.github.com/repos/spoho-datascience/idsse-data/git/trees/main?recursive=1
(no data files; 355 KB of processing and visualisation code)
```

Its README points back to figshare: *"Download the raw data
[here](https://doi.org/10.6084/m9.figshare.28196177)"*. There is no copy of the
match data on an allowed host. The dataset is roughly 2.4 GB across seven
matches, which no package registry would carry.

No local copy exists either: `find / -name "*idsse*"` returns only this project
and its zips, and `.data/` does not exist.

## What the companion repository does provide

The companion repository was supplied separately (`idsse-data-main.zip`, commit
`5c83f02`). It contains `data_processing.py`, `visualzation.py`, a
`data_summary.ipynb` whose stored output holds the authors' descriptive
statistics, and a `requirements.txt` pinning `floodlight==0.4.0`. It contains no
match data, and its README points to the same figshare DOI.

Its executed output is nonetheless useful, and is now shipped as
`reference/idsse_reference_counts.json`: 1,002,644 position frames, 11,137 event
rows, 5,241 `Play_Pass`, 140 `Play_Cross`, 207 players, 10 teams.
`verify/data_provenance.py` checks a parsed `work/` directory against those
totals as well as against the per-match frame counts, so the gate now rests on
the authors' own published census rather than on this project's assumptions.

Tested against the synthetic fixture, that check reports every total wrong
(84,000 frames against 1,002,644; 1,540 event rows against 11,137; no
`Play_Cross` at all) and the verdict stays `FIXTURE_OR_INCOMPLETE`.

Note also that the authors pin `floodlight==0.4.0` while this project needs
`>=1.2.0` for `floodlight.io.datasets.IDSSEDataset`, which did not exist in
0.4.0. Their scripts read local XML files directly
(`read_position_data_xml`, `read_event_data_xml`,
`read_teamsheets_from_mat_info_xml`), so if you download the figshare archive by
hand, those three functions are the path that needs no network access at all.

## What this means

Per the run instructions, there was no fallback to synthetic data, no fallback
to quick mode, and no fabricated numbers. The run simply did not happen.

To make it happen, the download host must be reachable. Either add
`ndownloader.figshare.com` to the network egress allowlist and rerun, or run the
pipeline on a machine with normal internet access.

## Running it yourself

```bash
pip install -r requirements.txt
python verify/reproduce_all.py --with-data --with-pretrain
```

If the machine you use also cannot reach figshare, download the archive by hand
from `doi.org/10.6084/m9.figshare.28196177`, keep the published filenames, and
set `IDSSE_DATA_DIR`:

```bash
export IDSSE_DATA_DIR=/path/to/figshare_xml
python verify/reproduce_all.py --with-data --with-pretrain
```

`common.load_match()` parses those XML files directly through `floodlight.io.dfl`
and makes no network call. This path was added after the companion repository
showed that the authors themselves read the files locally.

Budget for it: the first stage downloads ~2.4 GB and parses seven matches, which
takes a while; training is three seeds for the canonical run plus the ablation,
lead sweep, cross-offset matrix and size curve. A GPU helps, and the checkpoint
cache in `work/checkpoints/` means the sweeps reuse the canonical models rather
than retraining them.

For the ten-seed robustness rows on the important ablations:

```bash
python step12_ablation.py --robust
python verify/table4_ablation.py --robust
```

`config.ROBUST_SEEDS` is already `[0..9]` and `config.ROBUST_SETTINGS` already
covers space features, pretraining, both mirror conditions and the combined
setting.

## What will tell you the run is valid

Three gates, all of which fail closed. They were tested against the synthetic
fixture in this environment and all three behaved correctly.

1. **`verify/data_provenance.py`** compares each parsed match against the frame
   counts published in the dataset paper, plus framerate, DFL position codes and
   event identifiers. On the fixture it printed
   `frame count 12000 != 145967 published in the dataset paper: this is NOT the
   real match` and exited 1. On the real data it must print `verdict: REAL`.
2. **`verify/no_quick_results.py`** scans `work/` for quick-mode run ids in
   paper-facing files and fails if it finds any. On the fixture it reported 23
   contaminated paper-facing files and failed the whole pipeline.
3. **The provenance guard** already built into the verify scripts: changing a
   canonical constant changes the run id, and the verification refuses stale
   results. Tested by temporarily changing `LR`:
   `no predictions for run id quick-ed2dc90ca4. Run step23_canonical.py first.`

When all three pass, `verify/real_run_summary.py` writes
`work/REAL_RUN_SUMMARY.md` with **"Valid for paper reporting: YES"** at the top,
filled in from the generated CSV and JSON files. If either of the first two
gates fails, that line reads NO and says why.

## Known stage that will still not run

`step20_databallpy.py` needs the `databallpy` package, which pins numpy
incompatibly with floodlight. Install it in a separate environment, run that one
script there, and copy `work/databallpy_comparison.csv` back;
`verify/table3_sync.py` then produces the comparison table. Until then the stage
is recorded as not executed, and `REAL_RUN_SUMMARY.md` says so rather than
reusing an older number.

`step29_cross_provider.py` needs the PFF FC World Cup 2022 release. Without it
the script reports `dataset not available - not run`, which is the correct
outcome, not a failure.
